# NiuBot 产品架构

> 状态：现行（2026-11）｜配套：[技术架构](architecture.md)、[执行模型](execution-model.md)

## 1. 定位

NiuBot 是**常驻 IM 的人格化 AI 运行时**：把任意 CLI Agent 接进飞书，给它一个固定身份、长期记忆、可调度的任务和一套上下文自治机制，让它像一个长期同事那样持续工作。

**是什么**：个人或小团队的 AI 同事运行时；一条会话可以延续几个月；同一个进程托管多个 Bot 身份。

**不是什么**：

- 不是聊天机器人框架（面向开发者搭 bot 的 SDK）——它是可直接运行的产品
- 不是工作流引擎——没有 DAG、节点、编排器
- 不是多租户 SaaS——单机、单用户、私有部署
- 不是模型服务——不训练、不托管模型，只驱动现成 CLI Agent

## 2. 用户与场景

| 场景 | 用到的能力 |
|---|---|
| 长期对话，跨天/跨周记上下文 | 会话自治、长期记忆、归档检索 |
| 定时任务：早报、巡检、周报 | Cron（独立 session）+ 卡片推送 |
| 项目推进：多轮目标、反复打磨 | Goal + 正式任务 + 进度汇报 |
| 个人助理：提醒、查询、整理 | 记忆 + `nbt` 工具 + Skill |
| 多 Bot 协作：不同人格分工 | 协作回合 + 交棒 + 身份隔离 |
| 把外部能力装进来 | Skill（Markdown + CLI） |

核心用户是"一个人 + 多个 Agent 场景"，不是企业工单系统。

## 3. 三种会话关系

产品上只有三种，混淆这三种是设计错误的根源：

1. **主会话**（用户 ↔ Bot）：有记忆、有上下文、连续多轮；`/new` 才重置。
2. **独立任务**（系统 → Bot）：Cron、`/task` 用新 session 执行，结果回投来源会话，**不污染主会话**。
3. **协作回合**（Bot ↔ Bot）：多 Bot 在同一个群里按回合交棒，状态持久化，可恢复。

Loop 和 Goal 属于主会话的连续回合，不是独立任务。

## 4. 能力面

- **对话**：私聊、群聊、话题群、@、引用回复、合并连续消息
- **上下文自治**：自动新建、压缩、恢复、归档；用户不需要管 session
- **长期记忆**：用户偏好、完整会话归档、消息检索
- **任务与调度**：正式任务、Cron、Loop、Goal、进度汇报
- **工具**：`nbt` 全套（消息、任务、记忆、发送、控制）
- **人格**：Bot profile 定义角色/语气/边界；工作区 `AGENTS.md` 定义项目规则
- **运维**：`/restart`、`/update`、自动升级、保活、Bot 迁移
- **多 Bot**：一个进程多个身份，各有 DB、工作目录、backend、模型

## 5. 交互面

IM 就是 UI，没有独立前端。用户能看到的是：

- **一条最终回复**：回合内中间输出不直达，结束统一交付（Auto Delivery）
- **卡片**：状态、任务、进度、错误用结构化卡片，而不是长文本
- **footer**：session 短 id、token 占用、compact 状态、模型名——用来判断"它现在是什么状态"
- **命令**：`/new`、`/stop`、`/status`、`/task`、`/goal`、`/loop`、`/cron`、`/agent`、`/model`、`/effort`、`/restart` 等
- **主动消息**：回合内可用 `nbt send` 主动发文本/卡片/文件

## 6. 产品原则

1. **结果先行**：回合结束给一条完整结论，不碎片刷屏。
2. **用户不管上下文**：新建、压缩、恢复由系统决定；用户只在需要时 `/new`。
3. **人格与项目规则分离**：Bot profile（我是谁）和 workspace `AGENTS.md`（这个项目怎么做事）不混写。
4. **边界靠机制不靠自觉**：群聊不暴露私有记忆/任务、不跨会话串内容，是代码约束不是提示词。
5. **可观测**：`/status`、footer、运行态事件让"它为什么这样"可查。
6. **失败要显性**：超时、发送不确定、升级失败都有明确状态，不静默吞掉。

## 7. 明确不做

- **不以用户身份发消息**：Bot 只有自己的身份；代发属于越权。
- **不做通用工作流编排**：复杂流程用任务 + 调度 + Agent 组合。
- **不做 Web 管理台**：配置走文件与 CLI，界面就是 IM。
- **不做多租户**：一个进程属于一个人/一个团队，隔离靠进程而不是逻辑。
- **不做关系画像/数据挖掘**：只服务工作上下文，不做社交分析。

## 8. 与外部 Agent、Skill 的关系

- **Skill 是能力插件**：Markdown 说明 + 可调用 CLI，装在 Bot 工作区，Agent 按需读取。
- **`nbt` 是双向接口**：Agent 用它操作 NiuBot；外部 Agent（Codex、Claude Code）也能用它读写同一个 Bot 的数据。
- **外部数据层用 CLI 约定**：比如消息归档这类独立能力，产品上是"本机服务 + 只读 CLI + Skill"，NiuBot 不直连它的库。

## 9. 典型走查

**早报**：Cron 08:00 用独立 session 跑 → 组装 prompt → 生成卡片 → 回投私聊。主会话上下文不受影响。

**连续跟进一个项目**：主会话里多轮对话 → 触发 compact 后靠恢复提醒找回规则与任务 → 上下文继续。

**多 Bot 协作**：群里 @ 第一个 Bot → 按回合状态机决定下一个参与者 → 出站保证真实 @ → 中途中断可恢复。

## 10. 演进方向（未承诺）

- 第二个 IM 适配（当前抽象已就绪，但没有实现）
- 更统一的进展协议（当前靠卡片 + `/status` 拼）
- 外部数据源（消息归档、日历等）以 Skill + CLI 方式接入，而不是塞进引擎

以上是方向，不是排期；以任务 README 的当前状态为准。
