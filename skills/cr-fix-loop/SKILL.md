# Review-Fix Loop

代码质量收敛的循环工作流：**审查 → 修复 → 验证 → 再审查**，直到新一轮审查没有新增问题。

## 何时使用

- 用户要求"修一下 X"、"review 后修复"、"把这些问题都处理掉"
- 发版前的最后质量把关
- 有具体改动目标（修复 bug、重构、加功能）时的默认流程

## 工作流

```text
第 1 步 审查：对目标代码/改动做多角度审查：
        正确性（错误条件、null、缺 await、边界）
        并发与竞态（check-then-act、锁、时序）
        错误恢复（失败路径、回退）
        安全边界（注入、权限、敏感信息）
        清理（复用、简化、实现深度）
        每条发现附文件:行号证据，按严重度排序
第 2 步 修复：按严重度逐个修复（小步改动，保持可编译），
        每个修复说明改了什么、为什么
第 3 步 验证：跑测试/构建/复现，确认修复真实生效（以实际观察为准）
第 4 步 再审查：对修复后的代码重新审查，找新问题
→ 有新问题 → 回到第 2 步
→ 无新增问题 → 完成
```

## 循环规则

- **收敛标准**：新一轮审查**没有发现新增问题**即停止（存量已知边界/低优先项可接受）
- **进度汇报**：每轮开始与结束时都向用户简短汇报——
  - 开始：「第 N 轮审查中…」（用户知道在工作，不用干等）
  - 结束：「第 N 轮：发现 X 个问题 → 修复 M 个 → 验证通过」
  汇报简短，不重复细节
- **失败不掩盖**：测试失败如实报告，不因"修完了"跳过验证
- **成本控制**：连续两轮无新增问题就停，不做无限优化

## 执行方式

- **默认：逐轮接力**——每轮独立处理：审查用 subagent **同步等待结果**，该轮
  修复+验证完成后**回复用户汇报进度**（回合结束），下一轮继续（无需用户输入）。
  用户全程能看到轮次节奏，不会长时间无反馈
- **不适用**：预期超长（>5 轮）或需要后台运行（用户不在线）——此类场景改用
  Worker 派工：每轮 reviewer 审查 Job → 主 Agent 验收判断收敛 → 派下一轮（reviewer → developer → tester 依赖链）

## 输出

最终结论：循环轮数、修复问题总数、验证结果、剩余已知边界。
